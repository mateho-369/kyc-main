They are not interchangeable.

### Signed final event / retry guarantees and limits

- V2 `performer.approved` and `performer.rejected` contain schemaVersion, stable eventId, eventType, occurredAt, performer ID/external ID/status/kycStatus and stable owner Firebase UID/Sharegram ID. No names/email/reasons/document paths/images in these final-decision event payloads.
- Signature is HMAC-SHA256 over `${timestamp}.${exactJSONBytes}`; HTTPS, >=32-byte secret, configured host allowlist, public IPv4 pinning, no redirects/proxy. Test sender transport is mocked.
- Performer/decision/audit/outbox commit together. Concurrent decision calls serialize on the performer; a repeated terminal decision fails instead of creating another event. Failure before commit rolls back; failed delivery does not revert a committed decision.
- Retry is **at-least-once**, not exactly-once. Crash after remote acceptance can resend the same eventId. Receiver must atomically deduplicate/upsert by eventId/stable identity. No Sharegram receiver implementation is present to prove this or prove creator visibility.
- Exhausted/permanent failures remain `failed` records; monitoring and an authorized replay/runbook are still needed. There is no admin replay endpoint. DB/network/process-failure concurrency has only mocked tests here, not a real MySQL soak test.
- Legacy created/updated/deleted events remain a separate fire-and-forget V1 sender, with a different payload and weaker durability/privacy/egress properties. Do not confuse them with final-decision V2 guarantees. Delivery failure can lose those V1 notifications.
- Inbound signed read APIs preserve timestamp-bounded replay compatibility. There is **no durable ingress nonce/replay ledger**. Raw-body verification/idempotent business handling for any future decision ingress remains unimplemented; disabled handlers must not be enabled to bypass this.

Restore/confirm a correct UID binding through an authorized procedure. Existing operator seed-created unbound placeholders are not automatically linkable.

4. Use the real shared Firebase TEST project with the correct project/service account; never set emulator host. Firebase-origin refresh now requires reachable authoritative Firebase Auth and fails closed on outage. Existing access JWT validity is bounded by its expiry, not immediate Firebase revocation propagation.
5. Configure V2 destination URL/host allowlist/secret and operate the worker with monitoring. Confirm Sharegram V2 events, stable owner mapping, signature freshness, storage, deduplication and response semantics **before enabling real delivery**. Rotate any legacy keys that were logged/embedded previously and assess revocation of previously minted permissive custom tokens/claims; this patch does not erase historical exposure.
6. No seeds are required for this patch. Do not run bulk development seeds against shared/production databases. CLI admin promotion remains an operator-only capability with no invite, acceptance verification, Firebase claim synchronization or full provisioning audit workflow; prefer an already verified/bound real account and a reviewed operator action.
7. File paths must resolve inside `server/uploads/performers`. Audit legacy storage locations before rollout; references outside that root will now fail closed. Storage encryption, malware scanning, secure deletion/retention and dedicated document origin remain separate work. Do not auto-move/delete existing documents.
8. CORS now excludes null/plain HTTP production origins. Validate trusted reverse proxy HTTPS/origin/IP forwarding and distributed rate limiting; the new limiter is process-local. Comprehensive cookie-session CSRF policy, CSP tightening and WebSocket authentication/limits remain follow-ups, not covered by a six-width UI test.
